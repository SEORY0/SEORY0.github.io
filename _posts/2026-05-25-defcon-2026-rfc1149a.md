## TL;DR

1. 조류로 IP 패킷을 전송한다는 만우절 통신 프로토콜 표준(RFC 1149)을 구현한 문제로, 잔디밭에 찢어진 종이 조각 사진 14장이 주어진다.

2. 종이에 인쇄된 값들은 0x45로 시작하는 IPv4/TCP 패킷의 hex dump다.

3. 사진의 겹치는 구간과 IP ID, TCP Seq 필드를 기준으로 조각들을 이어 붙여 chunked·gzip으로 인코딩된 HTTP 응답을 살려낸다.

4. 복원된 HTML(GET /) → /static/style.css → @import에 숨겨진 비밀 호스트의 테마 CSS 순으로 리소스 참조를 따라가면 플래그가 나온다.

## 1. 배경

주어진 파일은 아래와 같은 사진 14장이며, 패킷 조각들이 여러 사진에 걸쳐 어지럽게 흩어져 있다.

{% include responsive-image.html path="/assets/images/rfc1149a/montage" alt="배포된 사진 14장의 몽타주" width=1200 height=1520 widths="480,800,1200" %}

각 종이 조각은 한 줄에 8바이트씩 끊어서 인쇄한 hex dump 형태다. 첫 조각의 시작이 `45 00 ...`이므로 IPv4 헤더가 맞고, 뒤이어 프로토콜 필드 `06`(TCP)을 지나 페이로드에 `HTTP/1.1 ...` 아스키 문자열이 이어진다. 즉, 단일 패킷 하나만 찍어둔 게 아니라 브라우저 세션 하나에서 오간 전체 HTTP 트래픽을 인쇄해 둔 것이다. 조각들을 제대로 이어 붙이기만 하면 HTTP 요청과 응답을 순서대로 살려낼 수 있다.

문제는 프로토콜 분석 자체보다 종이 조각을 눈으로 읽고 맞추는 노가다에 시간의 대부분이 들어간다는 점이다. 조각 크기가 손바닥만 한 데다 인쇄 해상도도 낮아서, 조각 하나만 놓고 봐서는 바이트 값을 정확히 판독하기가 꽤 까다로웠다.

## 2. 조각 재조립

복원은 크게 두 단계로 진행했다. 먼저 14장의 사진을 잔디나 낙엽, 겹쳐 찍힌 종이 조각의 위치를 기준으로 삼아 하나의 큰 지도처럼 이어 붙였다. 그다음 각 조각에 적힌 hex 값을 하나씩 읽어들였다.

{% include responsive-image.html path="/assets/images/rfc1149a/collection" alt="14장을 공간적으로 정합한 재조립 보드" width=2000 height=1499 %}

위 그림은 사진들을 하나로 합치는 데 사용한 작업 보드다. 붉은 점선은 각 사진의 테두리이고, 동그라미 표시가 사진끼리 겹치는 지점이다. 이렇게 전체 지도를 먼저 그려두면 특정 조각이 어느 사진들에 걸쳐 찍혔는지, 또 주변의 어떤 조각과 이어지는지 한눈에 파악할 수 있다.

개별 종이 조각을 이어 붙일 때도 비슷한 원리를 썼다. 종이가 칼로 깔끔하게 잘린 게 아니라 찢어지면서 나뉘었기 때문에, 조각의 끝부분 hex 값들과 다음 조각의 첫 부분 hex 값들이 살짝 겹치는 구간이 있었다. 이 중복 구간을 단서 삼아 조각들을 길게 이어 붙였다.

물론 사진을 확대해도 `8`/`9`/`6`, `b`/`8`, `e`/`c`가 도무지 구분되지 않는 글자들이 꽤 남는다. 이미지의 대비를 극단적으로 높여서 최대한 판독해 보고, 그래도 확신할 수 없는 바이트들은 후보군을 남겨둔 채 부록에 추정치로 표기했다.

조각들을 읽었다고 해서 무작정 이어 붙일 수는 없는데, 다행히 패킷 헤더에 있는 두 가지 필드가 훌륭한 정렬 기준이 되어주었다.

- IP Identification (IP ID): 복원한 조각들의 IP ID를 보면 `0x6196`, `0x619e`, `0x619f`처럼 연속된 값을 가진다. 브라우저가 순차적으로 주고받은 요청/응답 패킷들은 IP ID가 서로 인접하므로, 이 값을 기준으로 삼으면 각 조각이 어느 HTTP 메시지에 속하는지와 전체 순서를 알 수 있다.

- TCP Sequence Number (TCP Seq): 같은 TCP 스트림 안에서 쪼개진 페이로드들의 선후 관계는 TCP Seq 값으로 맞췄다.

이 두 필드가 14장의 사진에 흩어진 조각들을 몇 개의 HTTP 트랜잭션으로 묶어주는 인덱스 역할을 했다.

## 3. 패킷 파싱 — 첫 완성 조각 (`IP ID 0x6196`)

가장 먼저 온전한 형태로 복원해 낸 데이터그램이다. 운 좋게 사진 대비만 올렸는데도 조각 하나에서 패킷 하나가 거의 통째로 읽히는 경우가 있었다.

{% include responsive-image.html path="/assets/images/rfc1149a/img01" alt="한 조각에서 통째로 읽힌 패킷" width=2000 height=2656 display_width="55%" sizes="(max-width: 750px) calc(55vw - 22px), (max-width: 1024px) min(calc(55vw - 35.2px), 402.6px), 420.2px" %}

8바이트 단위로 정리한 헤더 영역(row00–row06)의 헥스 덤프는 다음과 같다.

```
row00: 45 00 01 80 61 96 40 00
row01: 40 06 17 b6 22 10 6f 0e
row02: 0a 0d 25 01 00 50 a5 86
row03: 01 0b 94 cf 9a ee b0 64
row04: 80 10 01 fe d8 c4 00 00
row05: 01 01 08 0a 00 18 ef 89
row06: 00 17 c9 1e 48 54 54 50   ; 뒤 4바이트 = "HTTP"
```

### 3.1 IPv4 Header (20 bytes)

| Offset | 필드 | 값 | 해석 |
|---|---|---|---|
| 0x00 | Version / IHL | `45` | IPv4, 헤더 20바이트 |
| 0x02 | Total Length | `01 80` | 384 |
| 0x04 | Identification | `61 96` | 0x6196 |
| 0x06 | Flags / Frag | `40 00` | Don't Fragment |
| 0x08 | TTL | `40` | 64 |
| 0x09 | Protocol | `06` | TCP |
| 0x0c | Source IP | `22 10 6f 0e` | 34.16.111.14 (서버) |
| 0x10 | Dest IP | `0a 0d 25 01` | 10.13.37.1 (클라이언트) |

목적지 IP인 10.13.37.1의 뒷자리가 13.37(leet)인 걸 보면, 실제 환경의 패킷을 뜬 게 아니라 문제 출제를 위해 세팅된 환경에서 캡처했음을 알 수 있다.

### 3.2 TCP Header (32 bytes)

출발지 포트가 `0x0050`(80번 포트)이므로 서버가 클라이언트에게 보낸 HTTP 응답 패킷이다. Data Offset 값이 `0x8`이라 TCP 헤더 길이는 32바이트이고, 플래그는 `0x10`(ACK)이다.

### 3.3 길이 정합

```
IP Total Length  = 0x0180 = 384
- IPv4 header    =          20
- TCP header     =          32
= TCP payload    =         332
```

계산한 페이로드 길이가 정확히 맞아떨어진다. 눈으로 읽은 헤더 바이트 값들에 오타가 없다는 걸 여기서 1차로 검증할 수 있었다.

## 4. HTTP / gzip 디코딩

이어서 페이로드 시작 부분(`row06`의 오프셋 4, `48 54 54 50`)부터 아스키로 변환해 보면 익숙한 HTTP 응답 헤더가 나타난다.

```http
HTTP/1.1 200 OK
Server: nginx/1.22.1
Date: Tue, 05 May 2026 14:47:10 GMT
Content-Type: text/html; charset=utf-8
Transfer-Encoding: chunked
Connection: keep-alive
Content-Encoding: gzip

15d
<1f 8b 08 ...>
```

헤더에 적힌 두 가지 인코딩 방식이 본문을 어떻게 복원해야 할지 알려준다. `Transfer-Encoding: chunked`가 적용되어 있으니 본문 첫 줄의 `15d\r\n`은 청크 크기(`0x15d` = 349바이트)를 뜻하고, `Content-Encoding: gzip`이므로 그 바로 뒤부터 `1f 8b 08`(gzip 매직 바이트, DEFLATE)로 시작하는 압축 데이터가 이어진다.

```
row30: 69 70 0d 0a 0d 0a 31 35   ; "ip\r\n\r\n15"
row31: 64 0d 0a 1f 8b 08 00 00   ; "d\r\n" + 1f 8b 08 ...
```

여기서 눈여겨볼 점은 gzip 스트림의 크기(349바이트)가 현재 패킷 하나에 담긴 전체 TCP 페이로드(332바이트, HTTP 헤더 포함)보다 크다는 것이다. 즉, 압축된 본문 데이터가 패킷 하나에 다 들어가지 못하고 여러 패킷(종이 조각)으로 쪼개져 있다는 뜻이다. 결국 흩어진 청크 본문들을 IP ID와 TCP Seq 순서에 맞춰 전부 이어 붙인 뒤에야 한 번에 `gunzip`으로 압축을 풀 수 있다. 14장의 사진을 전부 뒤져서 조각을 찾아내야만 했던 이유가 바로 여기에 있다.

조각들을 모아 압축을 풀면 아래와 같은 HTML 코드가 나온다.

```html
<!doctype html>
<html>
<head>
  <meta charset="UTF-8">
  <title>Home</title>
  <link rel="icon" href="data:image/svg+xml,...">
  <link rel="stylesheet" href="/static/style.css">   <!-- 후속 참조 -->
</head>
<body>
  ...
  <a href="/login">Login</a>
  <a href="/register">Register</a>
  ...
</body>
</html>
```

## 5. 리소스 참조 체인 추적

복원한 HTML에는 플래그가 없고, 대신 다른 리소스를 불러오는 링크들이 들어 있다. 즉, 브라우저가 페이지를 렌더링하면서 순차적으로 요청한 리소스들을 하나씩 따라가야 하는 구조다. 전체 추적 흐름은 다음과 같다.

`GET /` 응답을 복원한다. (IP ID `0x6196`)

HTML 내부에서 추가로 로드하는 리소스 경로를 찾는다. → `/static/style.css`

`/static/style.css`를 요청하는 패킷과 그에 대한 응답 패킷을 찾는다. (IP ID `0x619e` / `0x619f`)

응답 본문을 복원해 플래그가 있는지 확인하거나, 또 다른 리소스 참조를 찾아 따라간다.

앞선 과정과 똑같은 방법으로 `/static/style.css`의 응답 패킷(IP ID `0x619e`, `0x619f`)을 찾아 복원해 보면 다음과 같은 CSS 파일이 나온다.

```http
HTTP/1.1 200 OK
Content-Type: text/css; charset=utf-8
Content-Disposition: inline; filename=theme-light.css
...
```

```css
:root {
  --bg: #f5f5f5;
  --fg: #333;
  --heading: #1a1a2e;
  --card-bg: #fff;
  --card-shadow: rgba(0,0,0,0.1);
  --border: #ccc;
  --btn-bg: #1a1a2e;
  --btn-hover: #1621...;   /* 조각 경계에서 찢어짐 */
}
```

중요한 단서는 `style.css` 파일 맨 윗줄에 있는 `@import` 구문이다. 사용자의 다크/라이트 모드 설정(`prefers-color-scheme`)에 따라 서로 다른 테마 CSS를 불러오는데, 그 URL이 새로운 도메인을 가리키고 있다.

```css
@import url('http://supersecretflagserverdonttellanyoneaboutit.rfc1149.ctfwithbirds.com/static/theme-light.css') (prefers-color-scheme: light);
@import url('http://supersecretflagserverdonttellanyoneaboutit.rfc1149.ctfwithbirds.com/static/theme-dark.css')  (prefers-color-scheme: dark);
```

호스트 이름 자체가 대놓고 `supersecretflagserverdonttellanyoneaboutit`(아무에게도 말하지 말라는 초특급 비밀 플래그 서버)이다. 즉, 잔디밭에 흩어진 조각들 중에는 이 비밀 서버와 주고받은 요청·응답 패킷도 섞여 있다는 뜻이다.

남은 조각들 중에서 이 호스트로 보낸 `theme-dark.css`(또는 `theme-light.css`) 응답 패킷들을 찾아내 IP ID·Seq 순서로 묶고, 동일하게 `chunked`·`gzip`을 풀어주면 본문 안에서 최종 플래그를 얻을 수 있다.

전체 리소스 추적 경로를 요약하면 다음과 같다.

```
GET /                       (IP ID 0x6196)     -> HTML, <link href="/static/style.css">
  -> GET /static/style.css  (IP ID 0x619e/f)   -> @import url(… secret host …/theme-*.css)
       -> GET http://supersecretflagserverdonttellanyoneaboutit.rfc1149.ctfwithbirds.com/static/theme-dark.css
            -> 응답 본문에 flag
```

```
bbb{dear_bob_got_any_hot_goss_on_mallory_love_carol_ps_u_up?}
```

## 6. 정리

- 문제 유형 식별이 방향을 확정한다. 조각 선두 바이트 `45`와 제목의 RFC 1149, 이 둘이 "IPv4 hex dump 복원"이라는 결론을 즉시 준다.
- **IP Identification과 TCP Sequence**는 분절 조각을 HTTP 트랜잭션으로 접는 인덱스이다. 두 필드 없이 14장을 귀속·정렬하는 것은 불가능하다.
- 본문 복원은 chunked 해제 → gzip 결합 → `gunzip`의 순서를 요구한다. 청크가 데이터그램 경계를 넘으므로 조각 전량이 필요하다.
- 종단 리소스는 값이 아니라 **참조 간선**으로 도달한다. `<link href>`를 타 CSS까지 간 뒤에도, 색상 변수가 아니라 `@import url()`을 먼저 확인했어야 한다. 리소스를 타고 들어가는 문제에서 우선순위는 언제나 링크(link/import)이지 노드 내부 값이 아니다. 값 복원을 앞세우면 종단 도달이 지연된다.

> 판독이 갈린 바이트는 부록에서 `추정`/`후보`로 표기한다. 최종 호스트와 flag는 style.css의 `@import`를 사진 속 CSS 응답과 교차검증해 확정한 값이다.
